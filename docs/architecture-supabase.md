# Архитектура CORE и переход на Supabase

Дата фиксации решений: 23 ноября 2026 года.

CORE развивается на существующих HTML, CSS и JavaScript с модулями `import/export`. Сохраняются Python-сборка, GitHub Pages, оформление и языковые версии сайта. Supabase предоставляет авторизацию, рабочую базу карточек и API. Ниже описана целевая архитектура и порядок перехода; текущий кабинет пока использует демонстрационное хранение в браузере.

## Согласованный объём

На этом этапе подключаются четыре функции:

1. Регистрация, вход, выход и восстановление пароля через Supabase Auth.
2. Личный кабинет с реальной сессией и списком собственных карточек.
3. Создание и изменение собственных карточек датасетов с сохранением в БД.
4. Существующий каталог с загрузкой объектов из БД и сохранением оформления, поиска, фильтров и переводов.

Переход на Vue не выполняется. Отдельный Python-сервер, собственный серверный API и Edge Functions для этих четырёх функций не требуются. Сложная обработка файлов и другие серверные сценарии рассматриваются при появлении отдельного требования.

## Текущее устройство

- [src](../src/) содержит HTML-шаблоны. [tools/build_site.py](../tools/build_site.py) формирует опубликованные страницы, языковые версии, статические API и выгрузки.
- [assets/catalog-page.js](../assets/catalog-page.js) читает `window.CORE_CATALOG` из генерируемого индекса и управляет отображением и фильтрами каталога.
- [app/app.js](../app/app.js) объединяет экраны кабинета, маршруты, действия пользователя и демонстрационные сценарии.
- [assets/account-store.js](../assets/account-store.js) уже служит общей точкой состояния для кабинета и публичных страниц, но хранит записи в `localStorage`. Это демонстрационное состояние, а не подтверждённая сессия Supabase.
- Каталоги `api/`, `datasets/`, `ru/`, `uz/`, `hf/`, основные корневые страницы из `src/` и `sitemap.xml` создаются сборкой. Изменения их содержимого вносятся через исходники и генератор.

## Ответственность модулей

| Часть | Ответственность и основание |
| --- | --- |
| `api/supabase-client.js` | Создаёт один клиент для страницы, чтобы каталог, кабинет и состояние сессии использовали одинаковое подключение. |
| `api/auth.js` | Выполняет регистрацию, вход, выход и восстановление пароля через Auth. |
| `api/datasets.js` | Содержит общие запросы для каталога, кабинета и формы карточки, чтобы эти экраны работали с одной моделью данных. |
| `account-store.js` | Отражает сессию, полученную от Supabase, и сообщает об изменениях существующим потребителям. Управление токенами и обновлением сессии остаётся у SDK Supabase. |
| `pages/` | Координирует действия конкретного экрана: загрузку, фильтры, сохранение, ошибки и пустые результаты. |
| `ui/` | Формирует повторяемые элементы интерфейса. Выносится только то, что действительно используется повторно. |
| `supabase/migrations/` | Фиксирует структуру БД и права, необходимые для воспроизводимой настройки окружения. |
| `tests/` | Проверяет реальные сценарии, включая попытку изменить чужую карточку. |

Страница вызывает функции API-модуля и передаёт результат элементам интерфейса. В API-модулях нет обращений к DOM; разметка не содержит прямых запросов к Supabase. Состояние фильтров принадлежит странице каталога, состояние формы — экрану редактирования. Общая сессия проходит через существующий `account-store.js`.

Текущий контракт `load/save` синхронный и работает с целым локальным объектом. Для сети нужны асинхронные операции и ожидание результата в вызывающем коде. Его нельзя заменить удалённым сохранением всего демонстрационного состояния без переработки вызовов. При переходе сохраняются существующие точки подключения общего состояния, в том числе обновление ссылок на кабинет в шапке сайта.

## Взаимодействие с Supabase

Браузер обращается к Supabase через JavaScript SDK: Auth обслуживает пользователей и сессии, Data API — запросы к PostgreSQL. Для обычных операций над карточками используется [готовый Data API](https://supabase.com/docs/guides/api).

В `assets/config.js` хранятся URL проекта и [публичный publishable key](https://supabase.com/docs/guides/getting-started/api-keys). Административные ключи, пароль БД и параметры доступа к SMTP в опубликованные файлы не включаются.

Пользователи хранятся в Supabase Auth. Рабочие карточки хранятся в `datasets`; запись связывается с реальным пользователем через `owner_id`. При импорте сохраняются нынешние идентификаторы, названия и описания по языкам, организация, тип карточки, категории, лицензия, источник и ссылки. Представление ответа API при необходимости приводится к текущему формату карточки.

Права на таблицу и [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security) настраиваются совместно: вошедший пользователь создаёт карточки от своего имени и изменяет собственные. Подмена `owner_id` при запросе не должна позволять записать объект за другого пользователя или передать ему существующую запись. Фильтр на фронте помогает показать список собственных объектов, но ограничения исполняет БД. Выбор роли или организация в браузере не предоставляют административный доступ.

Публичный каталог читает разрешённые к публикации карточки. Собственные ещё не опубликованные записи, если такой режим будет выбран, доступны владельцу в кабинете. Конкретный момент публикации определяется до настройки соответствующих полей и политик.

## Рабочие сценарии

1. **Регистрация и вход.** Форма вызывает Auth. После подтверждения почты пользователь входит; кабинет и шапка сайта получают актуальное состояние сессии. Для писем реальным пользователям настраивается [собственный SMTP](https://supabase.com/docs/guides/auth/auth-smtp).
2. **Личный кабинет.** После получения сессии загружается список карточек пользователя. При обновлении страницы он восстанавливается из Auth и БД, а не из демонстрационного списка аккаунтов.
3. **Создание и изменение.** Форма передаёт поля карточки в API-модуль. При успешном сохранении обновляется интерфейс; при ошибке пользователь сохраняет введённые данные и получает понятное сообщение.
4. **Каталог.** Страница получает карточки из БД и применяет существующие поиск и фильтры. Новый объект можно открыть по ID с загрузкой данных из БД, без предварительного создания отдельного HTML-файла.

Поиск, сортировка, язык, ссылки и текущее представление каталога сохраняются. Способ загрузки и пагинации выбирается так, чтобы ограничения выдачи API не обрезали каталог незаметно для пользователя.

## Источники данных и сборка

После переключения рабочим источником карточек становится Supabase. Нынешние данные используются для первичного импорта; новые изменения карточек записываются в БД. `localStorage` больше не служит общей базой пользователей и рабочих карточек. Его использование SDK для сессии и интерфейсом для локальных предпочтений не заменяет серверное хранение данных.

Существующая Python-сборка продолжает создавать языковые версии, публичные HTML-страницы и выгрузки. Для карточек, перенесённых в БД, публичные представления получают согласованную публичную выборку из Supabase. Это сохраняет связь между каталогом, HTML-карточками, разметкой `schema.org/Dataset` и sitemap. В статические файлы не должны попадать закрытые данные кабинета.

Каталог получает новые разрешённые к публикации записи при очередной загрузке из API. HTML-страницы для поисковиков обновляются при сборке; автоматическое расписание их пересборки пока не согласовано. Статические API и пакеты остаются опубликованными выгрузками и не заменяют живой API Supabase.

При подключении ES-модулей обновляются исходные HTML и страница кабинета. Относительные пути должны работать и в языковых версиях, и под префиксом репозитория на GitHub Pages. Дополнительная сборка фронта не является обязательной частью перехода. Версия подключаемого SDK фиксируется.

## Порядок рефакторинга

1. **Разделить код с сохранением текущего поведения.** Оставить нынешние точки запуска, вынести запросы и повторяемый интерфейс в модули. Учесть уже существующие потребители `account-store.js`.
2. **Подготовить Supabase.** Получить доступ к выбранному проекту, настроить Auth, адреса возврата и почту. После решения вопросов публикации и владельцев создать модель карточек, права и RLS, сохранив изменения в миграциях.
3. **Подключить реальные сессии.** Заменить демовход и операции с локальными аккаунтами на Auth; переработать общее состояние и зависимые вызовы под асинхронное выполнение. Записи демонстрационных аккаунтов не импортируются как подтверждённые пользователи.
4. **Перенести карточки и переключить экраны.** Импортировать текущий каталог, подключить собственные карточки, создание, изменение и просмотр по ID. Переключить каталог на БД, сохранив интерфейс и языки.
5. **Согласовать публичные выгрузки и проверить переход.** Подключить публичные HTML-представления к тому же источнику данных, выполнить проверки сценариев и существующие проверки сборки, ссылок и JavaScript. Расширить проверку синтаксиса на новые модули.

## Критерии готовности этапа

- Регистрация, подтверждение почты, вход, выход и восстановление пароля работают на опубликованном сайте и при локальной проверке.
- Вход и обновление страницы дают согласованное состояние кабинета и ссылок в шапке сайта.
- Созданная карточка сохраняется в БД и доступна владельцу после повторного входа из другого браузера.
- Второй пользователь не может изменить чужую карточку или подменить владельца прямым запросом к API.
- Каталог показывает весь доступный набор карточек, сохраняет языки, поиск, фильтры и корректные ссылки.
- Видимость новой карточки соответствует отдельно выбранному правилу публикации.
- Новая карточка открывается по ID, даже если для неё ещё не собрана публичная HTML-страница.
- При сетевой ошибке интерфейс завершает состояние загрузки, сообщает об ошибке и позволяет повторить действие.
- Публичные выгрузки и страницы содержат только разрешённые данные; существующие проверки проекта проходят.

## Открытые решения и отложенный объём

До реализации зависимых частей требуется определить:

1. **Публикацию новых карточек:** сразу после создания или отдельным действием пользователя. Обязательная модерация не согласована.
2. **Владельцев импортированных карточек:** какие реальные пользователи получают право изменять существующие записи. Организация или источник карточки сами по себе не определяют аккаунт владельца.

Полный перенос избранного, заявок на доступ, операторской обработки, загрузки и защищённой выдачи файлов не входит в эти четыре функции и отдельно не согласован. Связанные демонстрационные сценарии должны оставаться явно отличимыми от работающей серверной интеграции. Готовность этого этапа не означает готовности всех сценариев кабинета.

Ранее обсуждавшиеся Vue, Vue composables, Vite и отдельный Python-бэк не входят в выбранный вариант. Собственные Edge Functions добавляются только для конкретной серверной операции, которую не обеспечивает выбранный механизм Auth, Data API и PostgreSQL.
