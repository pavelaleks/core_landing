# CORE: первый этап

Шесть таблиц приложения: `organizations`, `profiles`, `datasets`, `consumers`, `dataset_usage`, `licenses`. Аккаунты и пароли обслуживает Supabase Auth. RLS и разрешения входят в [первую миграцию](migrations/20261124100356_core_stage_one.sql) и [уточнение лицензий](migrations/20261124135523_dataset_licenses.sql).

## Данные и регистрация

- Импортированы 397 вузов с прежними ID `UNI-…` и отметкой подтверждения для демонстрации. Служебная организация CORE используется для собственных баз.
- При выборе вуза профиль ссылается на его запись. При регистрации компании создаётся новая организация с введённым названием.
- У новой компании и у нового пользователя `is_verified = false`. Отметки пользователя и организации независимы.
- Роли `contributor`, `coordinator`, `management` описательные: преподаватель/сотрудник, координатор данных, руководитель. Все работают со своими карточками; выбор роли не даёт административных прав.
- Существующий аккаунт без профиля завершает выбор организации после входа. Импортированные публичные карточки не назначаются ему автоматически.

## Подтверждение пользователя для демонстрации

В [панели Supabase](https://supabase.com/dashboard/project/jjwzntypllcumagzbdcn/editor) откройте `profiles`, найдите нужный `user_id` из Auth и установите `is_verified = true`. В кабинете пользователя нажмите «Обновить статус» или обновите страницу. Публикация после этого доступна владельцу карточки выбранной организации. Из браузерной формы изменить отметку нельзя.

Сохранение опубликованной карточки сразу обновляет её текст. Снятие с публикации скрывает её из живого публичного API. Черновики остаются доступны только владельцу. Отдельные процедуры профессионального аудита, отказа и отзыва подтверждения в демо не реализуются.

## Первоначальное наполнение и статические копии

Общий справочник `licenses` содержит три лицензии: `metadata-only`, `by-agreement`, `open-cc-by-4-0`. В каждой записи — локализованное название и пояснение, путь к существующему полному тексту и редакция 1.2. Это единые условия использования датасетов для университетов и компаний. Браузер читает справочник, но не меняет его; поддержка списка выполняется CORE.

Рабочая форма сохраняет `datasets.license_id`. Ручных полей названия лицензии, её URL и собственных общих условий больше нет. Внешний ключ исключает неизвестную лицензию; опубликованный пользовательский датасет обязан иметь выбранную лицензию. Для первых двух вариантов публичные ссылки типа `data` на файлы не допускаются. Черновики могут хранить такие материалы до подготовки публикации. Отдельные соглашения, согласия и S3 этим не реализуются.

Существующие 412 импортированных карточек сохраняют исходные `license`, `license_url`, `usage_terms`, а `license_id` остаётся пустым до отдельного осознанного назначения. Пользовательская сессия не пишет в старые поля лицензии. Тексты и подписи выбранной лицензии в каталоге, кабинете и сборке берутся из связанной `licenses`, без копирования в каждый датасет.

`node tools/prepare_supabase_seed.mjs` формирует `supabase/seed.sql` из публичных исходных данных и существующих связей графа. Применять его следует через доверенное подключение к БД. Скрипт не создаёт пользователей Auth и не импортирует рабочие карточки пользователей; повторный запуск не перезаписывает существующие записи.

Обновление публичных копий после изменений в рабочей БД:

```text
node tools/export_public_data.mjs
python -I tools/build_site.py
```

Экспорт обращается к Data API без пользовательской сессии и сохраняет только опубликованные карточки, общий справочник лицензий и доступные сведения об использовании в `data-src/public-catalog.json`. Связанная лицензия возвращается как `license_info`. Он не читает `profiles`. Сборка из этого снимка воспроизводима без сети; HTML, индекс каталога, `api/v0/public-catalog.json` и sitemap обновляются вместе. Новые пользовательские карточки открываются сразу через `app/index.html#dataset/<id>`; после экспорта и сборки получают также статическое представление.

Существующие отдельные API v0, образцы, Croissant и пакеты сохраняют прежний формат. Они являются опубликованными выгрузками, а не живым API. Автоматическое расписание экспорта и публикации сайта не настроено.

Потребители и связи из начального заполнения вымышленные и явно отмечены как демо. Первый тематический контент хранится в `data-src/digests.json`; таблица дайджестов, рассылки, рейтинги, карточки организаций и S3 для этого этапа не создаются.

## Проверки

```text
node --experimental-vm-modules tools/check_js.mjs
node --experimental-vm-modules --test tests/modules.test.mjs tests/auth.test.mjs tests/stage-one.test.mjs
python -I tools/build_site.py --check
python -I tools/check_links.py
python -I tests/test_build_modules.py
```

[tests/stage-one-rls.sql](../tests/stage-one-rls.sql) проверяет права непосредственно в PostgreSQL: запрет самоподтверждения и подмены владельца, изоляцию сотрудников одного вуза, публикацию после подтверждения и скрытие снятой карточки. Все его временные записи откатываются.

[tests/licenses-rls.sql](../tests/licenses-rls.sql) проверяет общий выбор трёх лицензий для вуза и компании, запрет изменения справочника и произвольной строки лицензии, внешний ключ и ограничения публикации. Все его записи также откатываются. Автоматические тесты проверяют сохранение ID вместо дублирования условий и отображение в трёх языковых версиях.

По решению пользователя от 24 ноября 2026 года подключение почты отложено. Форма запроса восстановления пароля вызывает Auth, обработка recovery-сессии проверяется тестами. Полный почтовый сценарий, доставку реального письма и адрес возврата проверяют после отдельного подключения почты. Текущий запуск охватывает регистрацию, вход и работу с карточками.

Советник Supabase повторно сообщил о прежних настройках проекта: правах вызова `rls_auto_enable()` и отключённой проверке скомпрометированных паролей. Эти настройки не менялись миграциями приложения; они отделены от проверенных прав шести таблиц. Справка: [права функций](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable), [защита паролей](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection).

## Почта, админка и подписка на новости

Миграция [20261125150000_admin_newsletter_mail.sql](migrations/20261125150000_admin_newsletter_mail.sql) добавляет:

- таблицу `newsletter_subscribers` (форма «Подписаться» в подвале сайта; посетитель может только добавить адрес);
- статус и заметку команды у `contact_requests`;
- таблицу `admins` и функции `admin_list` / `admin_update` для страницы [app/admin.html](../app/admin.html). Существующие права таблиц не меняются: админка работает только через эти функции, которые сначала проверяют `is_admin()`;
- письма команде о новой регистрации, заявке и подписке (через Resend API из базы, `pg_net`). Пока не заданы секреты, письма не отправляются, а ошибка письма никогда не мешает действию пользователя.

Миграцию применяют в SQL Editor Supabase или через `supabase db push`.

### 1. Корпоративный адрес

1. Ящик для команды, например `team@coredata.uz`: Яндекс 360, Zoho Mail или Google Workspace — тот, что удобнее. Провайдер сам подскажет MX-записи для DNS домена.
2. Если нужен только приём писем без отдельного ящика, хватит пересылки на личную почту (например, через ImprovMX или пересылку у регистратора домена).

### 2. Отправка писем (Resend)

1. Зарегистрироваться на [resend.com](https://resend.com), добавить домен `coredata.uz` и внести в DNS показанные записи SPF, DKIM и MX для поддомена отправки. Дождаться статуса Verified.
2. Создать API-ключ с правом Sending access.

### 3. Письма пользователям: восстановление пароля

В Supabase → Authentication → Emails → SMTP Settings включить Custom SMTP:

| Поле | Значение |
| --- | --- |
| Host | `smtp.resend.com` |
| Port | `465` |
| Username | `resend` |
| Password | API-ключ Resend |
| Sender email | `noreply@coredata.uz` |
| Sender name | `CORE` |

Authentication → URL Configuration: Site URL `https://coredata.uz`, в Redirect URLs добавить `https://coredata.uz/app/index.html`. Authentication → Emails → Templates → Reset Password: перевести письмо на русский. Ссылку `{{ .ConfirmationURL }}` оставить.

Кнопка «Забыли пароль?» на странице входа уже есть: она отправляет письмо, ссылка из письма открывает в кабинете форму нового пароля. Подтверждение email при регистрации не включать — текущая регистрация рассчитана на вход сразу.

### 4. Уведомления команде

В SQL Editor:

```sql
select vault.create_secret('re_ВАШ_КЛЮЧ', 'resend_api_key');
select vault.create_secret('pavel@coredata.uz, sasha@coredata.uz', 'admin_email');
select vault.create_secret('CORE <noreply@coredata.uz>', 'mail_from'); -- необязательно
```

Проверка: `select public.notify_admin('Тест', 'Проверка почты');`, затем посмотреть `select * from net._http_response order by created desc limit 5;`.

### 5. Админка

Назначить администратора (аккаунт должен быть зарегистрирован):

```sql
insert into public.admins (user_id) select id from auth.users where email = 'pavel@coredata.uz';
```

Затем войти в кабинет и открыть `https://coredata.uz/app/admin.html`. Разделы: заявки (статус, заметка), пользователи (подтверждение, имя, роль, организация), организации, датасеты (статус публикации, названия, описание, доступ, лицензия), подписчики. Удаления в админке нет: при необходимости — через панель Supabase.
